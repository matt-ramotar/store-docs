## Refresh workflow integration

The drift workflow is split across two runners. The `dokka-reference` job has
read-only repository permission, runs the Store6 checkout and complete
verification sequence, stages only trusted publication paths, and exports a
binary full-index patch plus bounded reports and checksummed metadata. The
write-capable `publish` job starts from a fresh `main`, independently derives
its target allowlist from that checkout, requires the artifact's target list to
match, applies the patch to the index, rechecks the patched lock and residue,
then creates one commit before exposing the token only to the final rolling-PR
step. Store6 code never runs in the token-bearing job.

The pre-release schedule and manual dispatch follow main. After the first
`6.0.0-alpha01` tag, scheduled runs become green no-ops and manual dispatches
require exactly one valid Store6 `6.x` release tag at the selected commit. A
release-tag regression now requires regeneration even when the tag points at
the already-pinned SHA and requires the support-matrix, overview-hash, and
release-notes decisions in the same PR. The release refresh is published only
to the rolling `docs-sync/repin` branch; its pull request is created or refreshed
before the workflow exits red for the required human editorial review.
